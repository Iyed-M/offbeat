# Spotify presentation metadata: compatibility gate (#79)

This is the compatibility decision for the current retriever outputs. New acquisitions write text and, where available, bounded Spotify artwork through `internal/tagging` before publication; existing-file refresh and metadata-change retagging are later slices. Reproduce the original generated-media picture/text probe (no downloaded or copyrighted media):

```sh
uv run --no-project --with 'mutagen==1.47.0' python scripts/verify_tag_compatibility.py
```

Requires `ffmpeg`, `ffprobe` and `metaflac` on `PATH` and access to the pinned Mutagen package on first run. Checked locally with FFmpeg/FFprobe n9.0.2, Metaflac 1.5.0 and Mutagen 1.47.0. The probe synthesizes a one-second tone per retriever extension in a temporary directory and a 2×2 original PNG in memory. It tags a **copy**, reads tags back with Mutagen, independently inspects tags with FFprobe/Metaflac and fixture-only binary readers, extracts the embedded picture with FFmpeg, compares codec/sample rate/channels and SHA-256 of independently decoded PCM before/after, then discards all fixtures. A passing decode digest demonstrates sample equivalence on these fixtures; it is not a proof of compatibility with every container variant or player. No actual Spotify Desktop responses, cover URLs or offline music-player UIs were tested.

The extension's `source` is `raw.item` when object-shaped, otherwise `raw`; it only uses the fields above, treats missing required fields/non-track/unplayable entries as unsupported placeholders, and does not collect extra presentation metadata. The tests in `spicetify/offbeat/offbeat.test.js` exercise synthetic Desktop shapes, not guarantees about optional fields on all Spotify builds. `parseCandidateSnapshot`/`materializeTrack` in `internal/app/adapter.go` require an exact field set, so adding an optional field needs coordinated extension, parser and persistence changes; simply sending extra JSON is rejected. `internal/desired/state.go` and `internal/db/desired_state.go` model current state only. `internal/db/migrations/0002_current_spotify_state.sql` stores URI, name, ordered artists JSON, album URI/name and duration; `0003_managed_tracks.sql` stores URI → relative path independently of desired-state removal. No credentials need to cross the adapter: keep all Desktop collection in Spicetify, transport only bounded normalized fields, and fetch any validated artwork URL without a Spotify token in the daemon. Do not infer that the current test fixtures establish availability of optional source fields in real Spotify Desktop data.

## Fixture-tested format matrix and field mapping

**Tooling decision:** use a narrow, version-pinned **Mutagen 1.47.0 Python helper** for tag writes across the five tagged formats, invoked by the Go daemon on a *new private staged copy*; do not build a new generic Go writer or use FFmpeg's generic attached-picture mapping for Opus. The helper is embedded in the Go binary and invokes `python3 -I` with a pre-provisioned Mutagen 1.47.0 installation visible to that interpreter. No `uv`, `pip`, package installation or dependency network fetch is run by the daemon. When Python/Mutagen is unavailable, audio is published intact and `managed_tracks.tag_state=failed` records an actionable bounded reason without a raw path or URL. FFmpeg/FFprobe are already configured for retrieval/inspection; Metaflac is **probe-only**, not a required daemon dependency. The staged pass has a 512 MiB input/output bound, 128 KiB metadata protocol, 30-second helper/probe/decode deadline and bounded child output/decoded PCM; before publication it compares audio stream codec/sample rate/channels and SHA-256 of decoded PCM. Artwork is passed to that same helper via a private, bounded file. The matrix picture cells are now exercised by both the #79 probe and native-tag tests of the acquisition writer.

### Offline runtime setup and required native-tag check

Prepare the wheel on a connected machine **before deployment**, then transfer the wheel directory to the offline Linux host. Use the Python version that will run the daemon; install `python3-venv` before going offline if your distribution needs it:

```sh
python3 -m pip download --only-binary=:all: --dest ./offbeat-wheels 'mutagen==1.47.0'
# On the offline host, with ./offbeat-wheels already transferred:
python3 -m venv "$HOME/.local/share/offbeat/tag-venv"
"$HOME/.local/share/offbeat/tag-venv/bin/python3" -m pip install --no-index --find-links=./offbeat-wheels 'mutagen==1.47.0'
"$HOME/.local/share/offbeat/tag-venv/bin/python3" -I -c 'import mutagen; assert mutagen.version_string == "1.47.0"'
```

Start `offbeatd` with `"$HOME/.local/share/offbeat/tag-venv/bin"` **first** on its `PATH` (for a systemd user service, set `Environment=PATH=/absolute/path/to/tag-venv/bin:/usr/local/bin:/usr/bin`). The daemon also needs its configured `ffmpeg` and `ffprobe` executables; they are not installed by this procedure. There is no daemon-time dependency installation. In the same environment, run the **required integration gate** before using real acquisitions:

```sh
PATH="$HOME/.local/share/offbeat/tag-venv/bin:$PATH" OFFBEAT_REQUIRE_TAGGING=1 go test ./internal/tagging ./internal/app -run 'TestStagedTextTagsAndUnchangedAudio|TestStagedNativeArtworkAndTextTags|TestAcquisitionTagOutcomeIndependentOfPlayableAudio' -count=1
```

This gate generates audio, independently reads actual native tags in all five supported formats, checks decoded audio integrity and tests the daemon's published FLAC tags. It **fails** if Python, pinned Mutagen, FFmpeg or FFprobe is absent. Ordinary `go test ./...` can skip the native-tag subtests when Mutagen is not provisioned; it is not a replacement for this gate. With a pre-cached wheel, this complete alternative is a *test invocation*, not a daemon runtime command:

```sh
uv run --offline --no-project --with 'mutagen==1.47.0' env OFFBEAT_REQUIRE_TAGGING=1 go test ./internal/tagging ./internal/app -run 'TestStagedTextTagsAndUnchangedAudio|TestStagedNativeArtworkAndTextTags|TestAcquisitionTagOutcomeIndependentOfPlayableAudio' -count=1
```

All five tagged formats retain their original audio codec, sample rate, channels and decoded PCM digest in the fixture probe. Synthetic album artist, numbers and date exercise **writer capability**, not availability in Desired Spotify state. Artist names and Spotify URI are test data; there are no real artist IDs in these files. No duration tag is written. For WAV/raw AAC, skip tagging and report unsupported metadata separately from audio availability; do not silently rewrap or re-encode to gain tag support. If an encountered variant or codec fails readback or audio verification, leave its original usable file alone and record a tag failure/unsupported status, not a missing track or acquisition retry.

**Independent inspection limits:** FFprobe confirms title, album and Spotify URI for all five tagged fixtures, and detects an attached-picture *view*; FFmpeg stream-copies that picture out and compares the PNG bytes. FFprobe's artist field joins the two values with `;` in Opus, Vorbis, FLAC and M4A, but returns only the first in MP3: it cannot prove that two distinct ordered values were stored. The probe therefore separately inspects the serialized Ogg comment packet for two ordered `ARTIST` entries, `SPOTIFY_URI` and a base64 FLAC Picture block (including Opus); Metaflac reports two ordered FLAC artist comments and URI and exports the FLAC picture; fixture-only direct ID3v2.4 frame inspection checks NUL-separated `TPE1`, `TXXX:SPOTIFY_URI` and `APIC` PNG bytes; direct MP4 atom inspection checks ordered `©ART` data atoms, freeform URI and `covr` PNG. These small binary readers are **fixture inspectors**, not production parsers or exhaustive malformed-file validators. The remaining synthetic optional tags have Mutagen readback and FFprobe normalization but not independent per-format raw-frame proof. Neither a media probe nor these inspections can establish how an arbitrary offline player displays multi-artist tags or custom URI fields.

## Safe handoff for later tickets

### #80 persistence gate

Migration 0008 adds nullable `album_artist`, `track_number`, `disc_number`, `release_date`, and `artwork_url` to current Spotify tracks. The normalized candidate accepts these as optional fields and bounds them; absent fields round-trip as absent, and existing candidates still parse unchanged. Title, ordered artist names, album, and duration continue to come from the existing Desktop shapes.

**Follow-up source evidence:** [Spicetify's `globals.d.ts` at 660a191](https://github.com/spicetify/cli/blob/660a1915e94004f7587e6ac6a30dcaec0ea63e63/globals.d.ts) defines `PlayerTrack.album.images?: {url, label}[]` and `PlayerTrack.metadata` with `album_artist_name`, `album_track_number`, `album_disc_number` (the latter two typed as strings). The extension now conditionally reads exactly `source.album.images[0].url` and those three `source.metadata` keys, whether `source` is the direct entry or `raw.item`. Empty/missing images or metadata yield absent optionals; malformed present values fail the whole candidate. It does not use `source.album.artists`, assume the first track artist is album artist, derive artwork from YouTube, or extract a release date: no documented release-date field was found on that type.

**Remaining verification gap:** Spicetify's [Platform docs](https://spicetify.app/docs/development/api-wrapper/methods/platform/) explicitly warn that internal APIs differ across Spotify Desktop versions and cannot give a complete API list; the upstream `Platform` type is `any`. `PlayerTrack` describes the player state, **not** the return types of `PlaylistAPI.getContents` or `LibraryAPI.getTracks`. The tests exercise documented conditional shapes on synthetic results for both collection paths, not real Desktop responses. Whether any of these keys are actually present on those two responses on the user's build remains unverified; a real, locally observed, redacted response or a verified API contract is needed to establish availability. No extra Spotify request is made to fill gaps. Artwork URL validation here only checks bounded HTTPS syntax; destination/redirect checks are required before any future fetch. Oversized or malicious present presentation values cause a collection error rather than demoting a supported entry to an unsupported placeholder; the daemon retains its previously committed candidate.

`internal/acquisition/retriever.go` stages one retrieved file in a private directory and FFprobes for readable audio. `internal/app/acquisition.go` invokes the embedded tag helper on a new private copy, checks unchanged decoded audio, then hands the verified descriptor to root-owned atomic publication. A text tag failure publishes the validated original and commits a durable `failed` tag outcome independently of audio completion; WAV/raw AAC commit `unsupported`. Interrupted staging never publishes. On retry or crash recovery, acquisition first opens the sole canonical orphan via the managed root, checks its container/codec with FFprobe and fully decodes it with FFmpeg using an inherited descriptor (30 seconds, 512 MiB input and 2 GiB decoded-output bounds), then commits its mapping without resolving or downloading again. An invalid/ambiguous orphan blocks replacement with a bounded repair/remove diagnostic; a valid recovered file gets `pending` tag and artwork status because its outcome cannot be inferred. `Available` remains a shallow nonempty/readability check for existing mappings, never the adoption criterion. Refresh still needs a safe root-confined existing-file read, atomic replacement and crash-safe bookkeeping. A source revision changing metadata must not change the SHA-256 path, download audio again or borrow titles/art from yt-dlp.

Bound normalized input lengths and artist count before persistence, reject controls that could inject M3U lines when displaying names, and keep optional fields absent rather than fabricating values. The original #79 fixture probe did not validate network retrieval, crash recovery, file replacement, realistic input sizes, player-specific display, or end-to-end daemon tagging; subsequent acquisition and artwork tests cover those boundaries except player-specific display.

### #82 artwork acquisition

`internal/artwork` accepts bounded HTTPS URLs without credentials, explicit ports, fragments or IP literals. It resolves on each connection, rejects any non-public or reserved resolved address, dials the checked IP while preserving hostname TLS verification, disables proxies, and rechecks at most three redirects. The total request has a 12-second deadline, 4-second handshake/header limits, a 5 MiB body cap, matching PNG/JPEG response and sniffed type, successful full decode, and at most 4096×4096 / 16 megapixels. A mutex-protected 32-image cache (at most 160 MiB) reuses validated bytes for the same album URI and URL within the daemon process. Neither raw URLs nor response errors are logged. Tests use a generated PNG and local TLS server with test-only loopback routing; no Internet image fixtures.

Migration 0010 records `artwork_state` (`pending`, `embedded`, `unavailable`, `unsupported`, `failed`) and bounded `artwork_error` independently of `tag_state` and audio availability. WAV/raw AAC are `unsupported`; absent URL is `unavailable`; failed fetch/validation or native embedding is `failed` and remains eligible for a future explicit metadata refresh. If picture writing fails, the same staging boundary retries text only. A canceled operation publishes nothing. A failed text pass publishes the original playable audio. An orphan after publication but before DB commit is recovered as `pending` for both outcomes. Artwork is never fetched to play an existing file. Existing-file refresh and state-change retagging are future tickets; this slice does not automatically retry a failed cover on an already managed file.
